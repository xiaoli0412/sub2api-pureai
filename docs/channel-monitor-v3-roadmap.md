# V3 渠道状态台：后续优化与拓展方向

> 配套文档：`channel-monitor-v3.md`（原理与移植说明）
> 本文只讨论**往哪里走**，按「投入产出比」排序，并给出落地位置与验证方式。

---

## 0. 一个关键线索：他的 V3 是个未完成的 MVP

移植时发现，他定义的 V3 文案里有 **6 个键从头到尾没被任何组件使用**：

| 未使用的 i18n 键 | 说明他原本想做什么 |
|---|---|
| `samples: '{count} 次请求'` | 在卡片上显示**样本量** |
| `healthScore: '健康度'` | 显示**健康度分数**（不只是状态徽章） |
| `healthy` / `warning` / `critical` | 健康度三档的**自有文案** |
| `allModels: '全部模型'` | **模型维度筛选** |

也就是说：样本量、健康度分数、模型筛选这三块，**文案已就位、脚手架已就位，只差接线**。
这直接决定了下面的优先级——先把「他自己想做完但没做完的」补上，成本最低、收益最直接。

## 方向一：把「样本量」摆到台面上（最低成本，最高收益）

**问题。** 现在卡片在 `health.overall === 'unknown'` 时只显示「样本不足」四个字，
但**为什么不足、差多少**完全看不到。而采样口径收紧到 `>10000 token` 之后，
样本不足会变成常态（见 `channel-monitor-v3.md` 4.1 与 10.1）。
用户看到「样本不足」时的第一反应是「监控坏了」，而不是「这个渠道大请求本来就少」。

**做什么。**
- 卡片上显示 `sample_count`（用已存在的 `channelMonitorV3.samples` 键，`MonitorMetric` 里有 `request_count`）
- 低于健康度阈值 `minimum_sample`（默认 50，见 `migrations/198_channel_monitor_v2_health_thresholds.sql`）时，
  显示「样本 12 / 需 50」而不是笼统的「样本不足」
- 时间轴上把样本量不足的柱子用**斜纹或降低不透明度**区分于「真的挂了」的红色柱子

**为什么优先。** 这是**信任问题**，不是功能问题。口径一收紧，样本量就是这套监控可信度的唯一解释来源。
不解释清楚，V3 的数字会被当成「不准」而弃用。

**落地。** `frontend/src/components/user/monitor/ChannelMonitorV3Card.vue` +
`features/channel-monitor-v2/monitorFormat.ts`。`MonitorMetric` 已含所需字段，后端零改动。

## 方向二：可用率下降时能下钻归因

**问题。** V3 只告诉你「这个分组可用率 87%」，不告诉你**为什么**。
排障还得切到别的页面。而错误分类数据**已经算好了**——`channel_monitor_v2_aggregation.go` 里的
`classified` CTE 已经把每个错误归到 `content_policy` / `authentication` / `context_limit` /
`rate_or_capacity` / `timeout` / `transport_or_stream` / `upstream_5xx` 等类别，
并且 `/channel-monitor-v2/errors` 接口**已经暴露**了它。V3 一次都没调用。

**做什么。**
- 卡片点击展开 → 该分组的错误分类分布（占比条 + 次数）
- 区分「我方问题」与「上游问题」：SQL 里已有 `upstream_affected` / `upstream_attempt_count` 字段，
  可直接显示「其中 N 次为上游故障」
- 高占比分类给出处置建议文案（如 `rate_or_capacity` → 考虑加账号或限流）

**为什么高价值。** 这一步把 V3 从「看板」变成「工具」。
从 87% 到「是 429 限流导致的」这中间的距离，就是监控有用和没用的距离。

**落地。** 新增 `ChannelMonitorV3ErrorBreakdown.vue`，复用 `api.getErrors(filter)`。
需要给 `/errors` 传 `group_id` 过滤器（接口已支持）。

## 方向三：双口径并行，消除「静默失败盲区」

**问题。** 这是当前口径**最大的软肋**：为了渠道间可比，我们只统计 `>10000 token` 的流式请求。
代价是**子 10k 请求的失败完全不进可用率**。如果某渠道专门在小请求上失败
（例如它对短 prompt 的路由配置坏了），V3 会显示 100% 可用。

**做什么。** 保留两套计数，而不是二选一：
- 严格口径（现有 rollup）：用于**渠道横向对比**与延迟/缓存
- 全量口径（新增一列或一张轻量 rollup）：用于**真实可用率**与告警
- 卡片上：主数字用严格口径，tooltip 或副标记显示「全量可用率 92.1%（含 1.2k 小请求）」
- 两者差异超阈值时给出提示：「该渠道小请求失败率显著偏高」

**为什么值得。** 严格口径解决「不可比」，全量口径解决「不漏报」。两个都要，因为它们回答不同问题。
只留严格口径是目前这套设计里唯一可能造成**真实故障被漏掉**的地方。

**落地。** `backend/internal/repository/channel_monitor_v2_aggregation.go`：
在两条 INSERT 里同时写一组 `*_all_requests` 计数列（migration 加列），
读侧 `channelMonitorV2Where` 不变。工作量中等，但这是**正确性**投资而非功能投资。

## 方向四：移植他的错误聚合性能改造（真正的隐患）

**问题。** 他为错误聚合超时修了**两次**（`535f7521f`、`3050134e7`），
说明这是他实际遇到的线上问题。上游当前版本**仍是**原始写法：

```sql
-- 现状（上游 v0.2.8）：每行都求值一次 IN 子查询
WHERE (... OR (current_error.request_id IN (SELECT request_id FROM candidate_ids) AND ...))
```

他的改法（更优）：
- 把 `candidate_ids` 提升到顶层 CTE
- 拆成 `eligible_errors` CTE，两条查找路径用 `UNION ALL` 分开
  （分支1：无 request_id 的，按时间；分支2：JOIN `candidate_ids`，按时间）
  → 两条路径都能走 `created_at` 索引，而不是逐行求值子查询
- 用**显式 23 列投影**替代 `SELECT e.*`
- `runOnce` 的整体超时 `55s → 2min`

**为什么建议做。** 这是**纯粹的性能与稳定性改造，不改变任何语义**（见下风险）。
错误聚合扫描的是高频日志表，随数据量增长，现在这版迟早会超时，
而超时的后果是**错误数据缺失 → 成功率虚高**，正好是最危险的失效方向。

**风险与注意。**
- 需要同步更新 `channel_monitor_v2_repo_test.go` 中对旧 SQL 形状的断言
  （他那边改了 `"current_error.created_at >= $1 - interval '90 minutes'"` → `"e.created_at >= ..."` 并新增 UNION 断言）
- `runOnce` 超时改成 `2min` 后**等于 leader 锁 TTL**，聚合可能活过自己的锁。
  因为写入是幂等 `ON CONFLICT DO UPDATE`，后果是重复劳动而非数据损坏，
  但更稳的做法是把锁 TTL 提到超时的 1.5 倍

## 方向五：渠道横向对比与基线告警

**问题。** V3 是「一个分组一张卡」的**并列**视图，没有**对比**视图。
当 8 个分组里有 1 个在劣化，用户得逐张卡片看时间轴才能发现。
而且目前没有任何告警——只有被动查看。

**做什么，分两步：**
1. **对比视图**：把选定分组的可用率曲线叠在同一张图上（颜色区分），TTFT 同理。
   时间轴组件已有 `availabilityBarClass` 与 tooltip 基础，可先做「多分组折线」版。
2. **基线偏移告警**：不要用固定阈值（`error_rate > 5%` 会在流量低谷集体误报）。
   用**分组自身的历史基线**：取过去 7 天同时间段（同小时/同星期几）的中位数，
   偏离超过 N 个标准差才告警。这样每个渠道跟自己比，天然消除流量结构差异。

**为什么。** 监控的终点是「不用盯着看」。目前 V3 需要人主动打开页面，
这在渠道数量增长后会失效。

**落地。** 对比视图纯前端；基线告警需要一张 `channel_monitor_v3_baselines` 表 +
聚合器里增加一个计算步骤，并接入既有通知渠道。

## 方向六：V3 专用后端接口

**问题（架构债）。** V3 现在**借用 V2 的接口** + `group_by=platform_group`，代价是：
- 每次刷新发 **2 个请求**（`snapshot` + `matrix`），服务端扫两遍
- 卡片在前端**自己算「最新桶」**（每个卡片排序 `buckets` 取最后一个，O(n log n) × 卡片数）
- V3 的语义（分组卡片、最新桶、归因）与 V2 的语义（平台/模型多维分析）开始分叉，
  却共享同一组接口，未来任何一方演进都会牵动另一方

**做什么。** 新增 `/channel-monitor-v3/*`：
- `GET /cards?range=90m` → 直接返回卡片所需的最终形状（含 `latest` 字段、样本量、错误归因摘要），
  前端不再做聚合计算
- 「最新桶」下推到 SQL（`DISTINCT ON (group_id) ... ORDER BY bucket_start DESC`），
  比在前端排 8 个数组更省
- V2 保持完全不动，两套接口各自演进

**为什么。** 这是「要不要长期维护 V3」的分水岭。如果只是尝鲜，不做也行；
如果要持续加功能（方向一/二/三都要加字段），继续挤 V2 接口会让两边都难改。

**注意。** 这会让 V3 与他的上游实现**脱钩**，将来同步他的更新会更费力。
建议**先做方向一/二**验证 V3 真的有人用，再决定是否投入这里。

## 方向七（可选）：选择性移植 V1 稳定性改进

他还有 3 处**与 V3 无关**的 V1 探测稳定性改动，本次**刻意没有移植**，因为会改变 V1 行为，
与本仓库「保留原 V1」的目标冲突：

| 改动 | 效果 | 风险 |
|---|---|---|
| 502/503/504 重试 3 次 + 250ms/500ms 退避 | 过滤上游瞬时抖动 | 每次探测最多多 2 次上游调用、+750ms |
| 连续 3 次硬失败才判定不可用（中间降级为 `degraded`） | 消除单次抖动误报 | **改变 V1 历史记录里的状态值**，`[failure-streak=n/3]` 会写进 message |
| 聚合器启动日志 + 首次循环 `passive_allowed` 日志 | 可观测性 | 几乎为零 |

**建议。** 前两项做成**独立开关、默认关闭**（例如 `channel_monitor_v1_transient_tolerance`），
这样默认行为与上游一致，需要的部署再打开。第三项（日志）无副作用，可随时直接收。

## 优先级汇总

| 序号 | 方向 | 投入 | 收益 | 建议时机 |
|---|---|---|---|---|
| 1 | 样本量可见性 | 低 | 高（信任） | **立即** |
| 2 | 错误归因下钻 | 中 | 高（可用性） | **立即** |
| 3 | 双口径并行 | 中高 | 高（正确性） | 近期 |
| 4 | 错误聚合性能改造 | 中 | 中高（稳定性） | 近期 |
| 5 | 横向对比 + 基线告警 | 高 | 高（自动化） | 中期 |
| 6 | V3 专用接口 | 中高 | 中（可维护性） | 有了真实使用后再做 |
| 7 | V1 稳定性（开关化） | 低 | 中 | 按需 |

**推荐路径：** 先做 1 + 2（成本低、直接补完他没做完的部分、立刻提升可信度），
再评估 3 + 4（正确性与稳定性投资），最后根据实际使用情况决定 5 和 6。
